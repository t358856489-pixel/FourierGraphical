# FourierGraphical 项目章程

## 核心原则

### I. 确定性优先: 图形是 (函数, 时刻) 的纯函数

任意时刻呈现的图形**必须**只由"当前傅立叶函数"与"当前时刻 t"决定, 与到达该时刻的路径无关.

- **禁止**逐帧累加旋转角度、轨迹点或任何其他随播放历史变化的渲染状态.
- 拖动时间轴到 t、从 0 连续播放到 t、循环回绕到 t、导出视频渲染第 t 帧, 四者的画面**必须**一致.
- 实时画布、图片导出、视频导出**必须**共用同一个绘制入口.
- 为性能引入的缓存**必须**与无缓存的整体重算逐点等价, 并有测试证明.

**理由**: 这是本产品正确性的根基. 关键帧、循环、时间跳转和视频导出的一致性由此按构造成立,
而不是靠多处状态同步勉强维持; 一旦破例, 这些功能会同时出现难以复现的偏差.

### II. 不可变数据与纯核心

- 所有领域数据**必须**是只读的; 任何修改**必须**返回新对象, 未涉及的部分保持引用相等.
- `src/core/` **必须**只包含纯函数: 不访问 DOM、时钟、随机数、存储或网络, 不修改入参.
- 可预期的失败**必须**以显式的结果类型返回, 附带面向用户的中文说明; **禁止**用异常表达业务失败,
  **禁止**静默吞掉错误.
- 来自系统边界的数据(本地存储内容、用户输入)**必须**在进入核心之前经过 schema 或范围校验.

**理由**: 撤销/重做基于快照, 渲染缓存基于引用相等, 两者都依赖不可变性. 纯核心使最关键的数学
可以在毫秒级、无浏览器的环境中被完整验证.

### III. 测试先行(不可协商)

- **必须**先写测试并亲眼确认它失败, 再写实现; 顺序为 红 → 绿 → 重构.
- 覆盖率门槛: 整体 **≥ 80%**, `src/core/` **≥ 95%**. 低于门槛的改动**不得**合并.
- 三类测试**必须**齐备: 单元(含对数学不变量的性质测试)、集成(存储与导出管线)、
  端到端(每个用户故事的"独立测试"至少一条).
- 测试失败时**必须**修实现而不是改测试, 除非能说明测试本身有错.
- 端到端测试**禁止**使用固定时长的等待; **必须**使用确定性的条件等待.

**理由**: 规范中的验收场景大多可以直接转写成断言. 先写测试能迫使接口在实现之前就想清楚,
也是原则 I 这类"按构造成立"的性质不被后续改动悄悄破坏的唯一保障.

### IV. 可访问性与键盘对等

- 画布上的每一项交互**必须**有一个表单控件形式的等价操作; 所有核心操作**必须**能仅用键盘完成,
  且焦点始终可见.
- 文字与图形元素的对比度**必须**满足 WCAG 2.2 AA.
- **必须**遵循 `prefers-reduced-motion`: 开启时不自动播放, 关闭装饰性过渡; 用户主动触发的播放仍然允许.
- 全局快捷键**不得**与获得焦点的控件自身的按键行为冲突.
- 自动化可访问性检查出现 serious 或 critical 级别的违规时, **不得**合并.

**理由**: Canvas 本身对辅助技术不可见. 如果不把"表单等价物"作为硬性要求, 可访问性会在每个新的
画布交互上被悄悄放弃.

### V. 性能预算

- 50 个分量且 10 个参数带关键帧时, 桌面**必须**保持 60 fps, 近三年的手机**必须**不低于 30 fps 且无可见卡顿.
- 参数变化到画面更新**必须** < 100 ms.
- 60 fps 的渲染路径**不得**经过 UI 框架的渲染周期.
- 首屏 JS **必须** < 300 KB(gzip), CSS **必须** < 50 KB; 只在个别功能中使用的重型依赖**必须**按需动态加载.
- 动效**必须**只使用合成器友好的属性(`transform`、`opacity`), **不得**对布局属性做动画.

**理由**: 这是一个实时交互的可视化工具, 卡顿直接破坏"调参数—看图形"的核心反馈回路.

### VI. 简单与本地优先

- 产品**必须**是无需安装、无需注册、无需服务器的纯前端应用; 用户数据**必须**只保存在用户自己的设备上.
- **不得**为尚不存在的需求构建功能或抽象(YAGNI). 引入新的运行时依赖、后台线程、后端服务或第二个项目,
  **必须**在实施计划的"复杂度跟踪"中写明理由和被否决的更简单方案.
- 已有经过验证的成熟库能满足需求时, **应当**优先采用而不是自行实现.
- 单个源文件**必须** < 800 行, 单个函数**必须** < 50 行; 代码**必须**按功能而不是按文件类型组织.

**理由**: 单人本地工具的价值在于"打开即用". 每多一层基础设施, 都会增加维护成本和故障面,
却不给用户带来可见的收益.

## 附加约束

**技术栈**: TypeScript(strict)+ React + Vite; 状态用 Zustand; 图形用原生 Canvas 2D;
样式用原生 CSS 与设计令牌. 更换其中任何一项属于需要修订章程的架构变更.

**安全**:

- 生产构建**必须**带严格的内容安全策略, 且**不得**加载任何第三方脚本; 字体**必须**自托管.
  该策略**必须**只作用于生产构建, **不得**破坏开发服务器.
- **禁止**使用 `innerHTML` 及其等价物; 用户输入的文本**必须**只作为文本节点渲染.
- 源代码中**不得**出现密钥或凭据; 应用**不得**发起指向第三方的网络请求.

**设计质量**:

- 界面**必须**有明确的视觉方向, **不得**呈现为未经设计的组件库默认外观.
- 颜色、字号、间距、时长**必须**通过设计令牌定义, **不得**在组件中重复硬编码.
- 字体**不得**超过两个字族. 每个分量的颜色是语义色, **必须**在列表、图形、时间轴中保持一致.
- 面向用户的文案**必须**为简体中文.

## 开发工作流与质量门禁

1. **规范驱动**: 功能**必须**依次经过 规范 → 澄清 → 计划 → 任务 → 分析 → 实施. 实施计划**必须**包含
   逐条对照本章程原则的"章程检查", 在研究前和设计后各评估一次.
2. **按用户故事增量交付**: 每个用户故事**必须**可以独立实现、独立验收、独立演示.
3. **合并前门禁**(全部通过才可合并): 类型检查、lint、全部测试、覆盖率门槛、包体预算、
   自动化可访问性检查.
4. **代码审查**: 每次改动之后**必须**进行代码审查; CRITICAL 与 HIGH 级别的问题**必须**在合并前修复.
   涉及本地存储读写、用户输入处理、文件导出的改动**必须**追加安全审查.
5. **提交**: 采用约定式提交 `<type>: <description>`, type 取
   `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`、`ci` 之一.

## 治理

- 本章程优先于项目中的其他实践与约定. 个人的全局编码规则作为补充: 与本章程一致处从其细节,
  冲突处以本章程为准.
- **修订程序**: 修订**必须**通过 `/speckit.constitution` 进行, 在文件顶部的同步影响报告中记录变更,
  并同步受影响的模板与进行中的功能文档.
- **版本策略**(语义化版本): 删除或重新定义原则 → MAJOR; 新增原则、新增章节或实质性扩展 → MINOR;
  澄清与措辞修正 → PATCH.
- **合规审查**: `/speckit.plan` 的章程检查与 `/speckit.analyze` 的章程对齐检查是强制门禁.
  与任何"必须"或"禁止"条款的冲突一律视为严重问题, **必须**通过修改规范、计划或任务来消除,
  **不得**通过弱化或重新解释原则来回避. 确有必要的偏离**必须**记入该功能计划的"复杂度跟踪",
  写明原因与被否决的更简单方案.
- 运行时的开发指导见仓库根目录的 `CLAUDE.md`.
