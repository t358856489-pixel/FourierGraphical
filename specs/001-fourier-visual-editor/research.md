# 阶段 0 研究: 傅立叶函数可视化编辑器

**日期**: 2026-09-21 | **规范**: [spec.md](./spec.md)

仓库是全新项目(只有 Spec Kit 模板), 没有既有技术栈需要兼容. 以下每项决策都对应技术背景中的一个未知项. 包版本于 2026-09-21 通过 `npm view` 核实.

---

## R1. 应用框架与语言

- **Decision**: TypeScript 7 (strict) + React 19 + Vite 8, 纯静态单页应用, 无后端.
- **Rationale**: FR-027 要求"浏览器打开即用、无需安装或注册", 假设章节确认数据只存本地, 因此不需要服务器. 界面有大量联动的表单控件(分量列表、关键帧、时间轴), 适合声明式 UI; 画布部分用命令式绘制(见 R3). 项目的全局编码规则已围绕 React/TSX、Zustand、Playwright 编写.
- **Alternatives considered**:
  - *Svelte / Solid*: 包更小, 但与既有规则和审查代理(react-reviewer)不匹配, 收益不足以抵消.
  - *无框架原生 TS*: 50 个分量 × 3 个参数 × 关键帧状态的控件同步手写成本高, 易出错.
  - *Next.js*: 无服务端需求, 引入 SSR 只增加复杂度.

## R2. 状态管理与撤销/重做

- **Decision**: Zustand 5. 拆成三个 store: `documentStore`(傅立叶函数, 可撤销)、`playbackStore`(时间状态, 不可撤销)、`viewStore`(视图设置, 不可撤销). 撤销/重做由 `src/core/history.ts` 中的纯函数实现: 保存不可变的函数快照栈(上限 50, FR-006), 连续拖拽在 pointer-up 时才提交一步.
- **Rationale**: 文档是不可变数据(全局规则要求), 快照即引用, 结构共享使 50 步历史的内存开销很小. 自己实现约 40 行纯函数, 可完全单测, 并能精确控制"一次拖拽 = 一步".
- **Alternatives considered**:
  - *zundo 中间件*: 可用, 但拖拽合并需要绕过其节流机制, 不如显式 `commit()` 清晰.
  - *Redux Toolkit*: 样板多, 对单人本地应用过重.
  - *命令模式(逆操作)*: 每种编辑都要写逆操作, 关键帧的自动创建(FR-018e)会使逆操作复杂化; 快照更稳妥.

## R3. 图形渲染

- **Decision**: Canvas 2D. 一个纯函数 `drawFrame(ctx, scene, t, view, size)` 负责全部绘制, 实时画布与视频导出(R6)、图片导出共用它. 画布由 `requestAnimationFrame` 循环命令式驱动, 直接订阅 store, **不经过 React 渲染**.
- **Rationale**: 每帧约 50 个圆 + 50 条线段 + 一条 ≤4000 点的折线, Canvas 2D 远未到瓶颈. 同一绘制函数用于导出, 保证"成片与画面一致"(FR-023b、故事 5 验收场景 4). 绕过 React 避免 60fps 下的协调开销, 满足 SC-002/SC-003.
- **Alternatives considered**:
  - *SVG*: 4000 点轨迹每帧重建 DOM 属性, 手机上掉帧; 且无法直接喂给视频编码器.
  - *WebGL / PixiJS*: 性能过剩, 增加包体与线条抗锯齿的复杂度.

## R4. 变频率下的旋转连续性 (FR-018f, FR-018g) —— 核心算法

- **Decision**: 向量角度定义为闭式表达式, 不做逐帧累加:

  `θ(t) = 2π · ( phase(t)/360 + ∫₀ᵗ f(τ) dτ )`

  频率轨道是分段函数, 三种过渡方式在每段上的积分都有闭式解(令 `u = (t−t₀)/Δ`, 段两端值为 `a, b`):

  | 过渡方式 | 值 `v(u)` | 段内积分 `∫ v dt` |
  |---|---|---|
  | 保持 | `a` | `Δ · a·u` |
  | 匀速 | `a + (b−a)u` | `Δ · (a·u + (b−a)·u²/2)` |
  | 缓入缓出 (smoothstep `3u²−2u³`) | `a + (b−a)(3u²−2u³)` | `Δ · (a·u + (b−a)·(u³ − u⁴/2))` |

  每条频率轨道预计算各段积分的前缀和, 任意时刻求值为一次二分查找 + 一次多项式计算, 即 O(log k). 首关键帧之前、末关键帧之后按常数外推(FR-018c). 圈数先对 1 取模再乘 2π, 保证长时间播放的精度(边界情况"时间值很大").
- **Rationale**: 闭式求值使"拖到时刻 t"与"连续播放到 t"**按定义相等**, FR-018f 后半句自动成立; 循环回到起点时状态由 `t` 唯一决定, FR-018g 自动成立; 模式切换、视频导出的逐帧渲染也都无状态. "缓入缓出"特意选用 smoothstep 而非 CSS 式三次贝塞尔, 因为后者的积分没有闭式解.
- **Alternatives considered**:
  - *逐帧累加 `θ += 2π·f·dt`*: 结果依赖帧率和播放路径, 拖动时间轴需要从 0 重放, 违反 FR-018f, 直接否决.
  - *数值积分(Simpson)*: 可行但有误差且更慢, 闭式解存在时没有理由采用.
- **验证方式**: 用 fast-check 做性质测试——对随机关键帧轨道, 闭式积分与高精度数值积分的差 < 1e-9; `θ` 在所有关键帧处连续.

## R5. 轨迹与波形的采样

- **Decision**: 轨迹是 `t` 的纯函数: 对区间 `[max(0, t − W), t]` 采样末端位置, `W` 为轨迹时长窗口(默认 8 秒, 视图设置可调), 采样率 = `max(60, 32 × max|f|)` 点/秒, 总点数上限 4000(超出则降低采样率), 末段按透明度渐隐. 波形视图使用同一批采样点的 y 分量, 横轴为 `t − τ`. 前向连续播放且文档未变时, 用环形缓冲只追加新采样点; 发生编辑、拖动时间轴、循环跳转、模式切换时整体重算.
- **Rationale**: 纯函数定义保证 FR-008a(切换模式按新模式重新生成)、重置后轨迹清空(区间在 0 处截断)、不闭合图形自动淡出(边界情况)全部自然成立. 采样率与显示帧率解耦, 所以高频分量的轨迹形状正确. 整体重算的最坏成本约 4000 点 × 50 分量 ≈ 20 万次三角函数, 桌面 <3ms; 环形缓冲把稳态播放成本降到每帧几十个点, 保护手机上的 SC-003.
- **已知限制**: 频率接近或超过显示帧率的一半(约 30Hz)时, 旋转向量本身会出现视觉混叠("车轮效应"), 轨迹不受影响. 这是显示设备的固有限制, 用户可通过降低播放速度(0.1×)观察. 记入 quickstart 的已知限制.
- **Alternatives considered**: *累积式轨迹(每帧把当前点 push 进数组)*: 最简单, 但与帧率耦合、拖动时间轴后轨迹错误、导出视频无法复现, 否决.

## R6. 视频导出 (FR-023a–d, SC-005a)

- **Decision**: WebCodecs `VideoEncoder` + **Mediabunny 1.x** 封装, 离线逐帧渲染: 对第 `i` 帧计算 `t = start + i · speed / fps`, 在离屏 canvas 上调用 `drawFrame`, 构造 `VideoFrame` 送入编码器, 根据编码队列长度做背压. 只输出 H.264/MP4; 若浏览器无 WebCodecs 或 `VideoEncoder.isConfigSupported` 不支持 H.264, 则禁用入口并说明原因(规范边界情况、FR-023d). 不提供 WebM 回退: WebM 在 iOS/Safari、QuickTime 与多数社交平台不能直接播放. 默认 1280×720 @ 60fps, 可选 1920×1080 与 30fps. 取消通过 `AbortSignal`. Mediabunny 通过动态 `import()` 按需加载, 不计入首屏包体.
- **Rationale**: FR-023b 要求"流畅度不受导出时设备性能影响", 只有离线逐帧渲染能做到; 配合 R4/R5 的无状态求值, 每一帧都是确定性的. H.264/MP4 是 FR-023d"主流播放器与社交平台直接播放"的最稳妥选择. `mp4-muxer` 已被官方标记为 deprecated 并指向 Mediabunny(已核实). WebCodecs 编码在 Chrome/Edge 94+、Safari 16.4+、Firefox 130+(桌面)可用. 硬件编码通常数倍于实时, 10 秒视频远低于 SC-005a 的 30 秒上限.
- **Alternatives considered**:
  - *`canvas.captureStream()` + MediaRecorder*: 实时录制, 设备卡顿会直接录进成片, 违反 FR-023b; 输出格式因浏览器而异.
  - *ffmpeg.wasm*: 约 30MB 下载, 远超包体预算, 编码速度慢一个数量级.
  - *在 Worker 中用 OffscreenCanvas 导出*: UI 更不受影响, 但字体加载与代码共享更复杂. 先在主线程做异步分片(每帧后等待编码队列/让出事件循环), 若实测进度条卡顿再迁移——`drawFrame` 是纯函数, 迁移成本低.

## R7. 图片导出 (FR-023)

- **Decision**: 在离屏 canvas 上以 2× 像素密度调用 `drawFrame`, `canvas.toBlob('image/png')` 后触发下载.
- **Rationale**: 复用同一绘制函数, 保证与画面一致; PNG 无损, 适合线条图形与教学材料.

## R8. 本地存储 (FR-021, FR-022)

- **Decision**: IndexedDB, 通过 `idb-keyval` 6 访问, 封装在仓储接口 `FunctionRepository`(`findAll / findById / save / rename / remove`)之后. 当前草稿在编辑后防抖 500ms 自动保存到独立键, 用于 FR-022 的恢复. 所有读取结果先经 Zod 4 schema 校验, 数据带 `schemaVersion`, 校验失败走"数据损坏"分支(提示并保持当前函数不变). 存储不可用(隐私模式)或写入失败时, 仓储返回显式错误, UI 提示原因, 编辑功能不受影响.
- **Rationale**: 最坏情况下单个函数约 7500 个关键帧 ≈ 300KB JSON, 十几个就会撞上 localStorage 的约 5MB 上限, 且 localStorage 是同步 API 会阻塞动画. 仓储接口使单测可以用内存实现替换. 全局规则要求"不信任外部数据、在边界做 schema 校验".
- **Alternatives considered**: *localStorage*: 见上. *Dexie*: 不需要查询与索引, 过重. *OPFS*: 兼容性与复杂度都不占优.

## R9. 可访问性 (FR-024, FR-025, SC-007)

- **Decision**:
  - 画布不可访问是前提, 因此**每一项画布交互都有表单等价物**: 拖拽向量端点(FR-004)对应振幅/相位的原生 `<input type="range">` + 数值框; 画布本身为 `role="img"` 并带动态摘要文本.
  - 时间轴上的关键帧标记是可聚焦按钮: 方向键移动时刻, Enter 编辑值, Delete 删除.
  - 播放控制快捷键: 空格 播放/暂停, `←/→` 步进, `Home` 重置, `Ctrl/Cmd+Z`、`Shift+Ctrl/Cmd+Z` 撤销/重做; 焦点在输入框内时不触发.
  - `prefers-reduced-motion: reduce` 时不自动播放, 界面过渡动效关闭; 用户主动点击播放仍可播放(这是内容而非装饰).
  - 当前时间读数不放进 live region(避免读屏器刷屏); 播放状态变化用 `aria-live="polite"` 播报一次.
  - 自动化: Playwright 中用 `@axe-core/playwright` 检查; 对比度在两套主题下均需通过 WCAG AA.
- **Rationale**: 这是让 Canvas 应用满足"仅用键盘完成所有核心操作"的唯一现实路径.

## R10. 样式与视觉方向

- **Decision**: 原生 CSS + CSS 自定义属性设计令牌(`src/styles/tokens.css`), 组件级样式文件与组件同目录; 不使用 Tailwind 或组件库. 视觉方向定为 **"实验仪器 / 示波器"**: 画布区是深色荧光屏质感(细网格、轨迹带余辉渐隐), 控制面板是暖色纸面质感的仪器面板, 分量颜色作为语义色贯穿列表、向量、关键帧标记. 字体两族: 一族无衬线用于界面(含中文回退到系统字体), 一族等宽用于所有数值读数; 自托管并子集化. 具体实现阶段使用 frontend-design 技能落地.
- **Rationale**: 全局设计规则禁止模板化外观, 要求明确的风格方向、语义化用色、把数据可视化作为设计系统的一部分. 示波器隐喻与产品内容(波形、旋转向量)天然契合. 深色画布 + 浅色面板也回避了"默认暗色模式".
- **约束**: 动效只用 `transform`/`opacity`; 首屏 JS < 300KB gzip、CSS < 50KB(应用页预算).

## R11. 测试策略

- **Decision**:
  - **单元(Vitest 5)**: `src/core/` 全部为纯函数, 目标覆盖率 ≥ 95%; 整体 ≥ 80%. 关键帧积分、循环、采样用 fast-check 做性质测试.
  - **组件(React Testing Library)**: 分量列表、关键帧编辑、输入校验(FR-005)、预设覆盖确认(FR-020).
  - **集成**: 仓储用 `fake-indexeddb` 测保存/恢复/损坏数据; 导出管线用注入的假编码器测帧数、时间戳、取消.
  - **E2E(Playwright 1.6x)**: 每个用户故事的"独立测试"各一条; 视觉回归截图断点 320/768/1024/1440; axe 检查; Chrome/Firefox/WebKit.
  - 严格 TDD: 先写失败测试再实现.
- **Rationale**: 规范的验收场景大多可直接转写为测试(如"第 2.5 秒振幅为 0.5"). 把全部数学放进无 DOM 的 `core/` 使最关键的正确性可以毫秒级验证.

## R12. 安全与部署

- **Decision**: 构建产物为纯静态文件, 可部署到任意静态托管. 严格 CSP(由 Vite 插件**仅在生产构建时**注入 `index.html`; 开发服务器需要内联样式与 WebSocket, 不注入): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; media-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'`. 无第三方脚本, 字体自托管. 不使用 `innerHTML`; 用户输入的函数名只作为文本节点渲染, 并限制长度. 具体托管平台不属于本功能的决策范围.
- **Rationale**: 应用没有网络请求与外部数据导入, 攻击面主要是本地存储内容的反序列化(由 R8 的 schema 校验覆盖)与函数名渲染.

## R13. 单位与取值范围

| 量 | 单位 | 范围 | 步长/精度 | 依据 |
|---|---|---|---|---|
| 时间 `t` | 秒 | `[0, ∞)` | 显示到 0.01 | FR-015 |
| 振幅 | 无量纲 | `[0, 100]` | 0.01 | FR-005, 边界情况 |
| 频率 | 圈/秒 | `[−100, 100]` | 0.001 | FR-001 |
| 相位 | 度 | `[−3600, 3600]` | 0.1 | 允许多圈, 以便关键帧做"额外转 N 圈"的过渡 |
| 播放速度 | 倍 | `[0.1, 10]` | 0.1 | FR-014 |
| 步进步长 | 秒 | 固定 1/60 | — | FR-015 |
| 循环区间最小长度 | 秒 | 0.1 | — | 边界情况 |
| 预设基频 | 圈/秒 | 默认 0.2 | — | 使 20 个分量的方波最高谐波约 7.8 圈/秒, 远离混叠 |

相位以"度"存储而非弧度: 这是用户输入与关键帧插值所用的量, 存储与显示一致可避免舍入漂移; 求值时才换算.
